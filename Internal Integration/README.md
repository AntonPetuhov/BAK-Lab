# Internal Integration

Решение Visual Studio: `Internal Integration.sln`. Название приложения: **Internal Integration**; технические имена проекта, исполняемого файла, службы: `InternalIntegration` / `InternalIntegration.exe`. Если ранее была установлена служба под прежним именем, ее регистрация автоматически не переименовывается.

## Фактическая структура и правила

В приложенном документе используется следующая структура (регистр значим):

```xml
<SafirMessage>
  <Requisition RequisitionID="synthetic-1">
    <ReqUnit AddressCode="32" />
    <Reply>
      <Sample LaboratoryID="1000097520IH">
        <Analysis TestMethodCode="IF_HIV_(2)" />
      </Sample>
    </Reply>
  </Requisition>
</SafirMessage>
```

Проверяется только непосредственный `Requisition/ReqUnit/@AddressCode`. Не используются `ReceiveUnit`, `SendUnit`, `CopyUnit1` или `Analysis/Lab`. Код находится в `Analysis/@TestMethodCode`, а лабораторный идентификатор — в родительском `Sample/@LaboratoryID`. Идентификатор для журнала: `Requisition/@RequisitionID` (это `requisitionID` из постановки задачи).

При `AddressCode="32"` точное значение `IF_HIV_(2)` заменяется:

| Sample/@LaboratoryID | Новый Analysis/@TestMethodCode |
| --- | --- |
| 1000097520IH | IF_HIV_(2)_1 |
| 1000097520IG | IF_HIV_(2)_2 |

Обрабатываются все `Requisition/Reply/Sample/Analysis`, без зависимости от позиции и количества. Неизвестные идентификаторы, другие коды и уже замененные коды сохраняются. Если нет единственного непосредственного `ReqUnit` с атрибутом `AddressCode` либо путь теста отличается от изученного, замена такого теста не выполняется, в журнал записывается количество неоднозначных тестов. Пространство имен берется у корня; элементы другого пространства имен не смешиваются с известной схемой.

Штатно одна пара соответствует одной заявке. Если XML содержит несколько непосредственных `Requisition`, каждый обрабатывается в собственном контексте, пара не разделяется. Для каждой заявки результат журналируется отдельной записью с ее идентификатором. В предоставленном примере `AddressCode="39"`: он проходит без изменений.

При нуле замен XML копируется исходными байтами. При заменах применяется безопасный XML-парсер и меняется только выбранный атрибут. Сохраняются значения других узлов, пространства имен, наличие декларации, standalone, кодировка и BOM. Пробельные узлы сохраняются, однако сериализация может нормализовать кавычки, сущности, переводы строк XML и форму пустых элементов. Побайтовая идентичность измененного документа, разумеется, не обещается. DTD и внешние сущности запрещены. Ограничение размера разбираемого XML — 64 млн символов. PDF никогда не разбирается, не изменяется, не генерируется и не встраивается; `Envelope/PdfCopy/@Path` также не меняется.

## Конфигурация

Все основные параметры находятся в `src/InternalIntegration/appsettings.json`. Относительные пути разрешаются относительно каталога приложения (`AppContext.BaseDirectory`), включая консольный режим. Они не зависят от текущей папки SCM. Файл конфигурации также читается из каталога приложения. Изменение настроек обработки требует перезапуска.

| Параметр FileProcessing | По умолчанию | Назначение |
| --- | --- | --- |
| InputDirectory | C:\XmlProcessor\Input | Входные XML/PDF, без обхода подпапок |
| OutputDirectory | C:\XmlProcessor\Output | Готовые файлы и внутренняя подпапка .staging |
| StateDirectory | C:\XmlProcessor\State | Постоянный журнал, защищенный ACL |
| ScanIntervalSeconds | 10 | Пауза между завершением обхода и следующим обходом |
| FileStabilitySeconds | 3 | Минимальная длительность стабильного размера и времени изменения |
| PdfWaitTimeoutSeconds | 300 | Ожидание PDF от первого обнаружения завершенного XML |
| RetryDelaySeconds | 5 | Минимальная задержка между попытками после ошибки |
| MaxRetryAttempts | 5 | Число ошибок до блокировки задания |

Пути не должны совпадать или быть вложенными друг в друга. Пустые пути, некорректные интервалы, отсутствие прав создания/удаления пробного файла и папки-ссылки отклоняются при старте. `PdfWaitTimeoutSeconds=0` разрешает немедленную обработку без отсутствующего PDF. Алиасы через ссылки в родительских каталогах, сетевые диски и альтернативные пути к одному тому не поддерживаются: администратор должен задавать обычные раздельные локальные пути.

## Ожидание и ошибки

Служба сканирует папку сразу при запуске и затем повторяет обход после паузы `ScanIntervalSeconds`. Используется один последовательный цикл без `FileSystemWatcher`, каналов и параллельных задач. Список файлов получается один раз за обход. Время обнаружения зависит от паузы и длительности предыдущего обхода. Файл считается готовым после стабильности размера и LastWriteTime и успешного открытия, запрещающего параллельную запись. Во время чтения исходники также открываются с запретом записи. Проверка готовности не блокирует ожиданием остальные заявки.

Первое обнаружение готового XML сохраняется в JSON-журнале на диске. Повторные обходы и перезапуск не сбрасывают срок. При перезапуске проверка стабильности начинается заново, исходный дедлайн остается. Если PDF обнаружен, этот факт сохраняется; даже после истечения срока обработка ждет готовности этого PDF. Заблокированный PDF не расходует попытки публикации. Если уже обнаруженный PDF затем удален, XML продолжает ждать его восстановления. Это предотвращает обход защиты от переноса неполного PDF.

Если PDF отсутствует после таймаута, XML обрабатывается один и публикуется без PDF; журнал содержит факт и `requisitionID`. Если PDF обнаружен только при первом сканировании после дедлайна, служба консервативно включает его и ждет готовности. Если PDF прибыл уже после публикации XML без PDF, он остается во входной папке для ручного разбора; самостоятельной догрузки позднего PDF нет. PDF без XML не удаляется. Фактическое ожидание может превышать таймаут на интервал сканирования, время восстановления стабильности и обработки очереди.

Поврежденный XML и конфликт имен блокируют только соответствующее задание; исходники остаются. Временные ошибки обработки повторяются с задержкой до `MaxRetryAttempts`, затем задание блокируется. Ошибки общего доступа к папкам/сохранению журнала протоколируются, сканирование повторяется. Невозможность открыть еще поступающий файл означает ожидание готовности. Некорректный файл журнала останавливает обработку всей очереди до исправления, чтобы не потерять информацию восстановления. Остановка использует `CancellationToken`; уже начатое синхронное чтение/хеширование/запись одного файла завершается до следующей точки отмены. Большие файлы увеличивают время остановки; XML хранится в памяти, PDF копируется потоком.

## Публикация и восстановление

1. Готовые исходники читаются с запретом параллельной записи. Проверяется отсутствие обоих целевых имен.
2. Результаты записываются в уникальную `Output/.staging/<transaction>/` и сбрасываются через `Flush(true)`.
3. В `StateDirectory` сохраняется журнал с хешами SHA-256, идентификаторами файлов NTFS, количеством замен, идентификаторами заявок и конкретными изменениями кодов. Журнал обновляется через временный файл и переименование.
4. Сохраняется намерение публикации PDF, затем его временный файл переименовывается в итоговый без перезаписи. После этого аналогично публикуется XML.
5. Сохраняется отметка `Published`. Проверяются хеши и идентификаторы обоих выходов; только после этого исходники удаляются с проверкой их хешей. Журнал удаляется последним.

Два отдельных файла нельзя опубликовать одной атомарной операцией файловой системы. Возможен промежуток, когда PDF уже виден, а XML еще нет. Потребитель должен считать появление XML сигналом готовности и игнорировать `.staging`. После сбоя транзакция продолжается по журналу; исходные файлы не нужны для повторной публикации уже подготовленных результатов. Сбой после удаления одного исходника также восстанавливается. Ожидаемые байты и сохраненный идентификатор NTFS отличают собственное переименование от чужого файла: даже посторонний файл с идентичными байтами считается конфликтом. Файл без записанного намерения публикации всегда считается конфликтом.

До успешной публикации обоих результатов исходники не удаляются. Нельзя модифицировать или удалять выходные файлы до завершения очистки службой; копирование потребителем допустимо. Входные имена не должны повторно использоваться поставщиком, пока задание активно. Папки State и `.staging` нельзя менять извне. Запись поставщиком через закрытие/повторное открытие с длительной паузой неотличима от завершения файла: рекомендуемый протокол поставщика — запись в отдельное временное имя и переименование после закрытия. Проверка стабильности сама по себе не может доказать, что поставщик больше никогда не продолжит запись.

Гарантия восстановления рассчитана на остановку/падение процесса при сохранности локального диска и журнала. Она не заменяет резервное копирование и не гарантирует сохранность при аппаратном сбое, потере питания/кэша контроллера или внешнем вмешательстве. Сбой перед записью журнала транзакции может оставить непривязанный каталог `.staging`; исходники при этом сохранены. Удалять такие остатки можно только при остановленной службе и после сверки ссылок `Transaction` во всех журналах. Не удаляйте журналы активных транзакций: это уничтожит сведения, отличающие восстановление от конфликта.

Для разблокировки: остановите службу, сохраните резервную копию исходников/журнала, устраните причину и в соответствующем JSON установите `Blocked=false`, `Failures=0`, `RetryAfter="0001-01-01T00:00:00+00:00"`. Не меняйте другие поля. Затем запустите службу. Для поврежденного исходного XML без подготовленной транзакции допустимо исправить исходник; при существующем `Transaction` исходник менять нельзя. Если выход был изменен извне, разберите задание вручную с отдельным новым именем; простое копирование резервной копии выходного файла изменит его идентификатор NTFS и не будет признано продолжением транзакции.

## Установка Windows Service

Команды выполнять в PowerShell **от имени администратора**, после копирования опубликованного приложения:

```powershell
sc.exe create InternalIntegration binPath= '"C:\XmlProcessor\App\InternalIntegration.exe"' start= auto DisplayName= "Internal Integration"
sc.exe description InternalIntegration "Обработка пар XML/PDF Safir"
sc.exe failure InternalIntegration reset= 86400 actions= restart/60000/restart/60000/restart/60000
sc.exe start InternalIntegration
sc.exe stop InternalIntegration
sc.exe delete InternalIntegration
```

Удаление службы не удаляет файлы или состояние. Перед обновлением приложения остановите службу и сохраните State.

По умолчанию `sc.exe create` использует LocalSystem. Для эксплуатации назначьте отдельную учетную запись во вкладке «Вход в систему» оснастки `services.msc` с правом «Вход в систему в качестве службы». Пароли в командную строку/README не записывайте. Учетной записи нужны чтение и выполнение каталога App; чтение, создание, запись, переименование и удаление в Input, Output, State, Logs, включая подпапки и файл блокировки. Поставщику нужны права на Input, потребителю — чтение Output. Исключите доступ посторонних к State и `.staging`: там есть технические метаданные и временные документы. Это также исключает подмену журналов.

## Простой текстовый журнал

Прикладной код напрямую вызывает `FileLogger.Info` и `FileLogger.Error`. Он не использует `ILogger`, фабрики, провайдеры или scopes. Внутренняя инфраструктура .NET Host остается частью Worker Service, но все стандартные выводы отключены вызовом `ClearProviders()` после `AddWindowsService`. Event Log не используется, создавать источник не требуется. Консоль в обычном режиме может оставаться пустой: события находятся в файле.

Единственная настройка журнала в `appsettings.json`:

```json
"FileLogging": {
  "DirectoryPath": "C:\\XmlProcessor\\Logs"
}
```

Относительный путь считается от каталога приложения. Нужны права на создание каталога и дописывание файлов. Журнал UTF-8: `InternalIntegration-20261012.log`; новый файл создается по дате UTC, время записывается со смещением `+00:00`. При перезапуске файл дополняется. Каждый вызов синхронно записывает и сбрасывает строку. Ротации по размеру и автоматического удаления старых журналов нет; архивирование организует администратор. Для разных экземпляров используйте разные папки Logs.

Примеры записей (имя и номер заявки синтетические):

```text
2026-10-12T12:00:00+00:00 | INFO | file=example.xml | requisitionID=test-1 | Начало обработки
2026-10-12T12:00:01+00:00 | INFO | file=example.xml | requisitionID=test-1 | Изменение опубликовано: LaboratoryID=1000097520IH; IF_HIV_(2) -> IF_HIV_(2)_1; количество=2
2026-10-12T12:00:01+00:00 | INFO | file=example.xml | requisitionID=test-1 | Пара XML/PDF опубликована
2026-10-12T12:01:00+00:00 | INFO | file=other.xml | requisitionID=test-2 | Без изменений: AddressCode=39
```

При отсутствии подходящих тестов записывается «Без изменений: подходящих тестов нет»; при неоднозначном отделении - соответствующая причина. Ошибки содержат имя XML, номер заявки, если его удалось прочитать, тип ошибки и номер попытки. Для поврежденного XML: `requisitionID=не определён`. Системные события используют `file=-`. Обработка без PDF отмечается отдельно. Пока файл не готов, цикл молча проверяет его при следующем обходе, не засоряя журнал повторяющимся ожиданием.

Подробности изменений записываются после проверки опубликованных результатов и до удаления исходников. Детали сохраняются в JSON-состоянии. При прерывании после записи строки журнала возможен ее повтор при восстановлении: текстовый журнал не является механизмом дедупликации. Для подготовленных заданий старой версии выводится сохраненное количество замен, если подробностей в старом JSON нет.

XML/PDF, ФИО и результаты анализов не выводятся. Тексты исключений парсера не пишутся. Имена файлов должны быть техническими и не содержать персональных данных. Переводы строк и разделитель `|` в значениях экранируются.

Если единственный журнал недоступен, программа останавливается с ненулевым кодом; короткая диагностика выводится в stderr без содержимого документов. Подготовленные данные и состояние сохраняются, автоматически откатывать уже опубликованные файлы программа не пытается. Исправьте права/доступное место и перезапустите службу. При отказе журнала после удаления части исходников сохраненное состояние завершит очистку при следующем запуске.

## Где читать код

| Файл | Назначение |
| --- | --- |
| Program.cs | Конфигурация, проверка путей, создание FileLogger и запуск Host |
| Worker.cs | Один цикл Scan → Task.Delay, остановка по CancellationToken |
| PairEngine.cs | CheckFilesReady → PrepareFiles → PublishFiles → DeleteSources |
| XmlTransformer.cs | Отделения, точечные замены и результаты для каждой заявки |
| StateStore.cs | Один JSON на задание; чтение, сохранение, удаление состояния |
| FileLogger.cs | Прямая запись строк UTF-8 в дневной файл |
| FileIdentity.cs | Проверка принадлежности опубликованного файла нашей транзакции |
| ProcessingOptions.cs | Параметры и проверка рабочих каталогов |

Методы и важные границы восстановления снабжены комментариями на русском. После обновления остановите прежний процесс, замените комплект приложения и сохраните прежние пути Input/Output/State. JSON прежней версии читается без обязательного нового поля Results. Старые настройки `Logging`, `Enabled`, `FileNamePrefix`, `MaxFileSizeBytes` больше не используются: перенесите только путь `FileLogging:DirectoryPath`.

## Проверки реализации

В текущей среде Windows с SDK 9.0.312 выполнена Release-сборка (0 предупреждений, 0 ошибок). Итоговый `dotnet test "Internal Integration.sln" -c Release --no-restore` прошел: 53 теста, 0 ошибок, 0 пропусков. Проверен также реальный рабочий цикл `BackgroundService` со сканированием существующей пары и штатной остановкой. Установка и запуск службы под SCM не выполнялись.

Автоматические тесты охватывают обе замены, произвольный порядок и повторы, неизменность байтов, другой код/лабораторию, повторно обработанные коды, пространства имен и несколько заявок, неоднозначную структуру, UTF-8/UTF-16/Windows-1251, DTD, разные порядки прихода, повторные последовательные обходы, сохранение таймаута, открытый PDF после таймаута, поврежденный XML/журнал, конфликты, отмену, блокировку второго экземпляра и восстановление на шести границах публикации. Также проверяются дневной текстовый журнал, детали замен и отсутствие изменений, недоступность журнала после публикации, приход файлов после запуска без событий и совместимость старого JSON. Отдельно проверяется чужой файл с идентичным содержимым после записанного намерения публикации.

Реальный запуск под SCM, учетную запись, доступ к текстовому журналу и перезапуск Windows необходимо проверить после установки на целевом сервере. Автоматические тесты имитируют прерывание на границах транзакции; они не имитируют физическую потерю питания.

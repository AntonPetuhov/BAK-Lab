# Internal Integration

Windows Worker Service на C#/.NET 9. Один `InternalIntegration.exe` запускается как служба или консольное приложение. Прикладной журнал пишет собственный `FileLogger`, без `ILogger`. Провайдеры журналирования .NET Host отключены.

## Согласованный упрощенный алгоритм

1. `Worker` последовательно сканирует входную папку при запуске и каждые `ScanIntervalSeconds` (по умолчанию 1 секунду). FileSystemWatcher, очередей и параллельной обработки нет.
2. Размер и время изменения XML должны оставаться стабильными `FileStabilitySeconds` (3 секунды). Проверяется возможность чтения с запретом записи другим процессом.
3. XML сразу разбирается, замены готовятся **в памяти**. Исходный файл не редактируется. В журнал попадают номер заявки и подготовленные замены либо отсутствие изменений.
4. С этого обхода начинается ожидание одноименного PDF: `PdfWaitTimeoutSeconds`, по умолчанию **10 секунд**. Повторные обходы не сбрасывают таймер. Ожидание одной заявки не мешает другим.
5. Если PDF обнаружен, ожидается стабильность его размера/времени и освобождение от записи, даже после таймаута. Если PDF так и не обнаружен, XML публикуется отдельно. Из-за периодического сканирования время ожидания округляется до следующего обхода; занятая служба может обнаружить файл позже его фактического появления.
6. Перед публикацией повторно проверяется хеш исходного XML. Если он изменился за время ожидания, подготовка и таймер начинаются заново.
7. Результаты записываются во временные файлы в выходной папке и сбрасываются на диск. Переименование публикует PDF первым, XML вторым. Существующие результаты не перезаписываются.
8. После успешной публикации всех результатов записывается итог и удаляются соответствующие исходники. PDF копируется байт в байт, не генерируется и не встраивается в XML.

**JSON-состояния и автоматического восстановления нет. После перезапуска отсчет начинается заново. Прерванная публикация требует ручного разбора.** PDF, поступивший после публикации XML без PDF, остается во входной папке; отдельная автоматическая досылка не реализована. Уже обнаруженный PDF, который исчез или остается занятым, ожидается до восстановления файла либо перезапуска.

## Структура XML и правила замены

Используются фактические поля предоставленного документа (регистр значим):

```xml
<SafirMessage>
  <Requisition RequisitionID="synthetic-1">
    <ReqUnit AddressCode="32" />
    <Reply>
      <Sample LaboratoryID="1000097520IH">
        <Analysis TestMethodCode="IF_HIV_(2)" />
      </Sample>
    </Reply>
  </Requisition>
</SafirMessage>
```

Внутри каждой `Requisition` должен быть ровно один непосредственный `ReqUnit` с `AddressCode`. Обрабатываются только ее `Reply/Sample/Analysis`. `LaboratoryID` находится **у родительского Sample**, код — в `Analysis/@TestMethodCode`, номер заявки — в `Requisition/@RequisitionID` (в журнале поле названо `requisitionID`). При неоднозначной принадлежности замены не выполняются, пишется диагностика. Пространство имен берется из корня.

При точном `ReqUnit/@AddressCode="32"` и `TestMethodCode="IF_HIV_(2)"`:

| Sample/@LaboratoryID | Новый TestMethodCode |
| --- | --- |
| 1000097520IH | IF_HIV_(2)_1 |
| 1000097520IG | IF_HIV_(2)_2 |

Все совпадения заменяются независимо от порядка и количества. Другие коды, лаборатории и уже измененные коды остаются без изменений. Несколько заявок внутри XML проверяются отдельно; весь документ остается одним выходным файлом.

`<!DOCTYPE SafirMessage SYSTEM "10repw.dtd">` **игнорируется** (`DtdProcessing.Ignore`, `XmlResolver = null`). DTD не загружается ни из файлов, ни из сети, не проверяется и не раскрывает сущности. Ссылки на сущности, определенные только в DTD, приводят к ошибке XML; стандартные XML-сущности работают.

Без замен возвращаются исходные байты, включая DOCTYPE, BOM и форматирование. При заменах XML сериализуется в исходной кодировке с сохранением наличия декларации, пространств имен и остальных значений. Игнорируемый DOCTYPE в измененный XML **не записывается**; оформление кавычек, переносов строк и пустых элементов может нормализоваться. Ограничение парсера — 64 млн символов. Подготовленные XML хранятся в памяти до публикации.

Предоставленная пара `007_2f18ef0c-2ded-4428-8b77-18c3ddcbc303` содержит `RequisitionID="1000097520"`, `ReqUnit AddressCode="39"`: замены не нужны, XML и PDF должны переноситься без изменения байтов. Исходные примеры в корне проекта не изменялись.

## Конфигурация и журнал

Настройки находятся в `src/InternalIntegration/appsettings.json`, после публикации — рядом с exe:

```json
{
  "FileProcessing": {
    "InputDirectory": "C:\\XmlProcessor\\Input",
    "OutputDirectory": "C:\\XmlProcessor\\Output",
    "ScanIntervalSeconds": 1,
    "FileStabilitySeconds": 3,
    "PdfWaitTimeoutSeconds": 10,
    "RetryDelaySeconds": 5,
    "MaxRetryAttempts": 5
  },
  "FileLogging": { "DirectoryPath": "C:\\XmlProcessor\\Logs" }
}
```

Все интервалы положительные, таймаут PDF допускает 0. Input и Output должны быть разными, невложенными папками; папки-ссылки не поддерживаются. Относительные пути считаются от каталога приложения, а не текущей папки Windows Service. Изменения настроек требуют перезапуска. При запуске создаются папки и проверяется возможность записи/удаления. Папку Logs размещайте отдельно.

Лог: `InternalIntegration-yyyyMMdd.log`, UTF-8, дата и время UTC, дописывается после перезапуска. Архивирование/удаление старых логов выполняет администратор. Лог доступен и при работе службы; Event Log не используется. При отказе записи лога обработчик останавливается.

Примеры полей строк (служебные события вне обработки файла используют `file=-`):

```text
file=a.xml | requisitionID=synthetic-1 | Начало обработки; XML подготовлен в памяти
file=a.xml | requisitionID=synthetic-1 | Подготовлена замена: LaboratoryID=1000097520IH; IF_HIV_(2) -> IF_HIV_(2)_1; количество=1
file=a.xml | requisitionID=synthetic-1 | Без изменений: AddressCode=39
file=a.xml | requisitionID=synthetic-1 | XML опубликован без PDF: срок ожидания истек; замен=0
```

«Подготовлена замена» означает результат в памяти; успешная запись подтверждается отдельным сообщением о публикации. Для поврежденного XML номер может быть `не определён`. Содержимое XML/PDF и данные пациентов не журналируются; текст исключений парсера также не выводится.

## Ошибки, конфликты и ограничения

- Поврежденный XML и конфликт имен блокируют только соответствующий XML до перезапуска. Исходники не удаляются; другие заявки продолжают обрабатываться.
- Временные ошибки до публикации повторяются не чаще `RetryDelaySeconds`, максимум `MaxRetryAttempts`. После исчерпания попыток нужно устранить причину и перезапустить. Файл, еще открытый для записи, просто ожидается без расходования попыток.
- Второй экземпляр для той же входной папки блокируется файлом `.processor.lock`.
- **Два файла не публикуются атомарно.** Между PDF и XML возможен сбой. Любой существующий итоговый файл, даже с совпадающими байтами, считается конфликтом. Автоматически отличать свой частичный результат от чужого сервис больше не пытается.
- После сбоя остановите службу, сохраните копии входных и выходных файлов, проверьте журнал. Для повторной обработки перенесите конфликтующие выходные файлы в отдельную архивную папку и оставьте полную исходную пару во входе; затем запустите службу. Если выходная пара уже полная, решите вручную, нужна ли повторная отправка потребителю. При сбое между удалениями исходников один из них уже может отсутствовать — восстановите комплект из проверенных выходов/резервной копии до повторного запуска.
- Остатки `.*.xml.tmp` / `.*.pdf.tmp` после аварийного завершения не публикуются автоматически. Проверять и удалять их следует при остановленной службе. Существующие результаты автоматически не удаляются.
- Перед переходом со старой версии остановите ее и разберите незавершенные задания из прежних `State` и `.staging`. Новая версия их не читает. Не запускайте две версии на одной рабочей папке.
- Проверка стабильности не гарантирует завершение работы отправителя, если он закрывает файл между порциями на срок больше интервала. Предпочтительный протокол отправителя: запись под временным расширением и итоговое переименование. После передачи файла нельзя заменять/удалять его другим процессом. Используйте локальные папки Windows с предсказуемой семантикой блокировок и переименования. Потребитель должен начинать с появления XML.

## Сборка на другом компьютере через Visual Studio

Пошаговая инструкция: [PDF-руководство](<output/pdf/Internal Integration - Руководство.pdf>). PowerShell для сборки не нужен.

1. Установите Visual Studio 2022 17.14 с поддержкой .NET и .NET 9 SDK через Visual Studio Installer. Скопируйте решение вместе с папками `src` и `tests`.
2. Откройте `Internal Integration.sln`. Восстановите NuGet-пакеты через контекстное меню решения (нужен доступ к источникам пакетов).
3. Настройте `appsettings.json`. Выберите Release / Any CPU → **Сборка → Собрать решение**.
4. **Тест → Обозреватель тестов → Запустить все**. Тесты используют синтетические данные.
5. Назначьте **Internal Integration** запускаемым проектом. F5 — отладка, Ctrl+F5 — консольный запуск. Для проверки кладите во вход только копии примеров: успешно обработанные исходники удаляются. Ctrl+C в консоли — штатная остановка.
6. Контекстное меню проекта → **Опубликовать → WindowsFolder → Опубликовать**. Профиль: Release, net9.0, win-x64, Self-contained, без single-file и trimming. Перенесите **всю папку** `publish/win-x64`, затем настройте пути на целевом компьютере. Отдельный .NET Runtime для автономного комплекта не требуется.

Сборка/публикация не устанавливает службу. Профиль лежит в `src/InternalIntegration/Properties/PublishProfiles/WindowsFolder.pubxml`.

Альтернативные команды для разработчика (можно выполнять в cmd.exe):

```bat
dotnet build "Internal Integration.sln" -c Release
dotnet test "Internal Integration.sln" -c Release
dotnet run --project src\InternalIntegration
dotnet publish src\InternalIntegration\InternalIntegration.csproj -p:PublishProfile=WindowsFolder
```

## Установка Windows Service

В **cmd.exe от имени администратора**, после копирования опубликованной папки в `C:\Services\InternalIntegration`:

```bat
sc.exe create InternalIntegration binPath= "C:\Services\InternalIntegration\InternalIntegration.exe" start= auto DisplayName= "Internal Integration"
sc.exe start InternalIntegration
sc.exe stop InternalIntegration
sc.exe delete InternalIntegration
```

Остановка должна завершиться до удаления регистрации/замены файлов. Учетную запись задайте в оснастке `services.msc` → служба → Свойства → Вход в систему. Ей нужны чтение/выполнение папки приложения, чтение/создание/удаление файлов в Input и Output, создание и запись в Logs, а также право входа в систему как служба. Для сетевых ресурсов нужны отдельные права доступа; подключенные диски пользовательской сессии службе не видны. Проверка реального запуска под SCM в рамках этой доработки не выполнялась.

## Навигация по коду

`Program.cs` читает настройки и запускает Host. `Worker.cs` вызывает `PairEngine.Scan` и делает паузу. `PairEngine.cs` проверяет готовность, вызывает `XmlTransformer.Transform`, ожидает PDF и публикует результат. `XmlTransformer.cs` применяет только правила XML. `FileLogger.cs` синхронно дописывает строки в дневной файл. `ProcessingOptions.cs` проверяет настройки. Старые `StateStore.cs` и `FileIdentity.cs` удалены.

Порядок вызовов и разбор примера: [разбор кода](<docs/Разбор кода Internal Integration.md>).
